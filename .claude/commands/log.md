# /log — 개발일지

팀 깃허브에 남길 **하루치 개발일지**를 쓴다.
노션 회고와 역할이 다르다. 여기는 **오늘 무엇을 왜 그렇게 했는지의 기록**이고, 회고는 주 단위 감상이다. 둘을 섞지 마라.

이 일지는 **포트폴리오로 쓰인다.** 그래서 "무엇을 했다"보다 **"왜 그렇게 판단했는지"**가 본문이다.
한 일만 나열한 일지는 커밋 로그와 다를 바 없어 가치가 없다.

## 1단계 — 사실을 직접 수집한다

**사용자에게 "오늘 뭐 하셨어요?"라고 묻지 마라.** 그건 네가 알아낼 수 있다.

날짜는 인자로 받고, 없으면 `date +%F`로 오늘을 쓴다. **날짜를 추측하지 마라.**

```
git log --since="<날짜> 00:00" --until="<날짜> 23:59" --pretty=format:'%h %s'
git log --since=... --until=... --stat
git status --short
```

- **git 저장소가 아니면** (`fatal: not a git repository`) 거기서 멈추지 말고, 커밋 정보 없이 진행한다.
  대신 사실 요약 자리에 `git 저장소 아님 — 커밋 기록 없음`이라고 적고, 오늘 만들어진 파일을 `ls -lt`로 확인해 대신 쓴다.
- **오늘 커밋이 0개여도 진행한다.** 디자인·문서·조사만 한 날도 일지가 필요하다. 그런 날은 "커밋 없음. 작업 내용은 아래 답변 기준"으로 적는다.
- 커밋 메시지가 `wip`, `수정`처럼 내용이 없으면 `git show --stat`으로 실제 바뀐 파일을 보고 네가 요약한다.

## 2단계 — 요약을 보여주고 세 가지를 묻는다

수집한 사실을 **두 줄 이내**로 압축해서 먼저 보여준다. 형식:

```
오늘 커밋 4개: 색상 토큰 정의, Button 컴포넌트, 화면 07~09 토큰 연결
tokens.css 신규, 12개 파일 수정
```

그 다음 아래 세 질문을 **한 글자도 바꾸지 말고** 그대로 출력한다.

```
세 가지만 답해주세요:
1. 오늘 막혔거나 예상과 달랐던 게 있나요?
2. 판단이 갈렸던 지점이 있나요?
3. 팀에 물어볼 게 생겼나요?
```

**여기서 멈춘다.** 답을 기다리지 않고 일지를 쓰지 마라. 질문을 더 붙이지도 마라.
"없음"이라는 답도 정상이다. 되묻지 말고 그대로 받아들여라.

## 3단계 — 파일을 쓴다

`docs/devlog/<날짜>.md`에 아래 형식으로 쓴다. 이미 있으면 **덮어쓰지 말고 읽어서 이어 붙인다.**

```markdown
# 2026-09-08 (화)

## 한 일

- 색상 토큰 15종 정의 (`src/styles/tokens.css` 신규)
- `Button` 컴포넌트 — variant 4 × state 4
- 화면 07~09의 하드코딩 색을 토큰으로 교체

커밋 4개 · 12개 파일 수정

## 판단

### 회색을 9종에서 3종으로 줄임

피그마에 회색이 9종 있었지만 실제로 역할이 구분되는 건 3종뿐이었다.
`#999` `#aaa` `#bbb`는 같은 자리에 섞여 쓰였을 뿐 의도된 구분이 아니었다.
9종을 그대로 토큰화하면 다음에 색을 고를 때 매번 헤매게 되므로
`--text-secondary` `--text-muted` `--border-default` 셋으로 통합했다.

## 막힌 것 / 예상과 달랐던 것

- (없으면 이 섹션 자체를 뺀다)

## 내일

- `TextInput` `Toggle` 컴포넌트

## 팀에 물어볼 것

- 백엔드: DB가 RDS MySQL인지 → `status.md` Delegate에 추가함
```

### 쓸 때 지킬 것

- **"~했습니다" 말고 "~했다".** 기록체로 쓴다.
- **"판단" 섹션이 이 문서의 본체다.** 사용자가 2번에 "없음"이라고 답해도, 1번 답이나 커밋에서 판단이 읽히면 그걸 판단 섹션으로 올려라.
  예: "회색이 9종인데 3종만 썼다"는 관찰이지만, 그래서 3종으로 통합했다면 그건 판단이다.
- **근거를 한 줄이라도 붙인다.** "토큰으로 통합했다"로 끝내지 말고 "왜 그게 나은가"를 적는다. 포폴에서 읽히는 건 그 한 줄이다.
- **사용자가 말하지 않은 걸 지어내지 마라.** 특히 소감·난이도·성장 서사. 답이 짧으면 일지도 짧게 끝낸다.
- **자기평가를 쓰지 마라.** "뿌듯했다", "많이 배웠다" 같은 문장은 넣지 않는다. 사실과 판단만 남긴다.
- 파일·컴포넌트·토큰 이름은 **실제 이름 그대로** 쓴다. 나중에 코드에서 검색이 돼야 한다.
- 길이는 **화면 한 장**을 넘기지 않는다.

### 「알게 된 것」을 쓰는 법

1번 답이 **"몰랐던 걸 알게 됐다"**로 나오면 `## 알게 된 것` 섹션을 만들어 쓴다.
처음 하는 협업이라 이런 게 매일 나온다. 포폴에서 잘 읽히는 부분이기도 하다. **다만 쓰는 법이 중요하다.**

- **교과서 설명을 쓰지 마라.** "API란 서버와 통신하는 방식이다" 같은 문장은 검색하면 나오는 내용이라 가치가 없다.
- **내 작업에서 실제로 부딪힌 지점으로 쓴다.** 무엇을 하다가 → 무엇을 몰랐고 → 그래서 뭘 바꿨는지.
- **한 항목 3줄 이내.** 길어지면 설명글이 되고, 그건 일지가 아니다.
- 그날 실제로 겪은 것만 쓴다. 공부한 것, 읽은 것은 여기 쓰지 않는다.

```markdown
## 알게 된 것

- 목데이터를 화면 안에 직접 쓰면 나중에 연동할 때 화면을 전부 뒤져야 한다.
  `src/lib/mock/`에 몰아두면 그 파일 내부만 fetch로 바꾸면 된다는 걸 알고 구조를 옮겼다.
- ERD에 컬럼이 없으면 API가 그 값을 줄 수 없고, 결국 화면에 못 띄운다.
  로고 컬럼이 없는 걸 오늘 발견했다. 디자인을 다 그린 뒤였으면 다시 그릴 뻔했다.
```

**나쁜 예 — 이렇게 쓰지 마라**

```markdown
- 오늘 API에 대해 공부했다. API는 프론트와 백엔드가 데이터를 주고받는 약속이다.
  많이 배웠고 앞으로도 열심히 해야겠다.
```

무엇을 하다가 알게 됐는지가 없고, 그래서 뭘 바꿨는지도 없다. 검색 결과와 다를 게 없다.

## 4단계 — 3번 답을 처리한다

"팀에 물어볼 것"이 나왔으면:

1. **먼저 `docs/`와 `status.md`에서 이미 답이 있는지 확인한다.**
   이미 정해진 걸 또 물으면 팀 시간을 뺏는다. 답이 있으면 일지에 그 사실을 적는다.
   예: `백엔드에 Supabase를 왜 쓰는지 물으려 했으나, 9/8에 EC2 자체 서버로 확정된 사안이었다.`
2. 아직 답이 없으면 `status.md`의 **Delegate 목록에 항목을 추가**한다.
3. 일지에는 "→ `status.md` Delegate에 추가함"이라고만 남긴다. 질문 내용을 두 곳에 길게 쓰지 마라.

## 5단계 — 보고

작성한 파일 경로 한 줄만 출력한다.

```
docs/devlog/2026-09-08.md 작성했습니다.
```

일지 내용을 대화창에 다시 붙여 넣지 마라. 파일을 열어 보면 된다.

## 하지 말 것

- 커밋하거나 push하지 마라. 사용자가 따로 시킬 때만 한다.
- 노션에 쓰지 마라. 노션은 주 단위 회고 전용이다.
- 없는 날의 일지를 소급해서 만들지 마라. 인자로 명시된 날짜만 쓴다.
